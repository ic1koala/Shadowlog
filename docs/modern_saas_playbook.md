# モダンSaaS開発 ＆ プロジェクト推進 総合プレイブック
## GitHub × Vercel × Supabase を用いた高速開発・アーキテクチャ・やること管理ノウハウ

---

## はじめに
本ドキュメントは、Next.js、GitHub、Vercel、Supabase、および外部決済・AI APIを組み合わせてWebサービス（SaaS）を迅速かつ安全に立ち上げ・スケールさせるための**システム設計アーキテクチャ**および**プロジェクト推進（やること管理・意思決定）のノウハウ**を体系化した汎用プレイブックです。

新規事業や別プロダクトの立ち上げ時に、技術選定、チーム分業、コスト管理、データ整合性、タスク管理の標準テンプレートとして活用できます。

---

## 第1章：システム構造 ＆ インフラアーキテクチャ

### 1. 全体パイプライン（GitHub ➔ Vercel ➔ Supabase）

```
[開発環境 / AIエージェント]
        │
        ▼ (git push)
  ┌───────────┐
  │  GitHub   │ ➔ バージョン管理・Pull Request・CI自動テスト (Vitest / Jest)
  └─────┬─────┘
        │ (Webhook自動連携)
        ▼
  ┌───────────┐
  │  Vercel   │ ➔ Next.js App Router (ホスティング・CDN・Edge/Serverless Functions)
  └─────┬─────┘
        │
        ├────────────────────────┬────────────────────────┐
        ▼                        ▼                        ▼
 ┌──────────────┐         ┌──────────────┐         ┌──────────────┐
 │   Supabase   │         │    Stripe    │         │  外部API /   │
 │ (DB/Auth/RLS)│         │(決済・サブスク)│        │  AI基盤      │
 └──────────────┘         └──────────────┘         └──────────────┘
```

#### ① なぜこの構成が最強なのか？
- **インフラ管理工数ゼロ（サーバーレス）**:
  OSアップデートやサーバー監視、スケーリング対応が一切不要。ユーザーが0人の時はほぼ無料、トラフィック急増時も自動スケール。
- **デプロイの自動化と安全性**:
  GitHubにコミットしてプッシュするだけで、Vercelが自動ビルド・静的最適化・プレビュー環境生成を行い、本番反映まで数分で完了。
- **バックエンドの即時立ち上げ**:
  Supabaseにより、PostgreSQLデータベース、認証（メール/Google OAuth等）、ファイルストレージ、リアルタイム通信が一元提供される。

---

### 2. オフラインファースト ＆ クラウド二重化設計

B2Cや習慣化SaaSでは、「ネット環境が不安定でも快適に動く」「登録前にすぐ試せる」ことがCVR（登録率）と継続率を大きく左右します。

```
【未ログイン時 (ゲスト)】
  ユーザー操作 ➔ ブラウザ LocalStorage / IndexedDB に一時保存 (超高速・即時)

【ログイン / 会員登録時】
  認証完了 ➔ LocalStorage のデータを Supabase クラウドへ自動アップロード (データ移行)

【複数端末利用時 (PC / スマホ)】
  ログイン時 ➔ Supabase クラウドから最新データをダウンロード ＆ マージ
```

#### 実装のポイント:
1. **ゲスト体験（登録不要体験）**:
   最初の数回は会員登録なしで利用させ、感動体験を与えた後に「クラウド保存・端末間同期」をフックにして会員登録を促す。
2. **クラウドへの自動引き継ぎ (Migration)**:
   未登録時に端末に溜まった利用履歴を、ログイン成功時にバックグラウンドでSupabaseのレコードへ一括INSERTする。
3. **オフライン耐性**:
   オンライン復帰時に未送信データを非同期でDBに同期する仕組みを設けることで、電波の途切れによるユーザーの離脱を防止する。

## 第2章：セキュリティ ＆ データ整合性の鉄則

### 1. Row Level Security (RLS) の徹底
Supabaseの最大の特徴は、フロントエンドから直接データベースを叩ける手軽さですが、**RLS（行単位セキュリティ）を有効にしないと他人のデータを改ざん・閲覧される致命的事故**に繋がります。

- **全テーブルで `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;` を適用**。
- **基本ポリシー**:
  ```sql
  -- 本人のみ読み取り可能
  CREATE POLICY "Users can view own data" ON public.user_records
    FOR SELECT USING (auth.uid() = user_id);

  -- 本人のみ書き込み可能
  CREATE POLICY "Users can insert own data" ON public.user_records
    FOR INSERT WITH CHECK (auth.uid() = user_id);
  ```
- **管理者処理の分離**:
  全顧客の集計や定期処理は、サーバーサイドAPIからのみ呼び出せる `SUPABASE_SERVICE_ROLE_KEY`（管理者秘密鍵）を用いて安全に実行する（ブラウザ側に絶対に露出させない）。

---

### 2. 決済情報の完全非保持化 (PCI-DSS準拠)
個人開発やスタートアップで自社サーバーにクレジットカード番号を保持・通過させることはセキュリティ・法務上、絶対に避けるべきです。

- **Stripe Checkout / Customer Portal の全面採用**:
  カード入力画面はすべてStripeが提供する堅牢なUIを使い、自社サイトは一切触らない。
- **Webhookによる非同期ステータス更新**:
  Stripe側での決済完了・解約・更新イベント（`invoice.payment_succeeded`, `customer.subscription.deleted` 等）をWebhookで受け取り、Supabaseのユーザーテーブルのプラン区分を自動更新する。

---

### 3. 環境変数の管理とサーバーレスの特性理解
Vercel等のサーバーレス環境では、以下の点に注意が必要です：

- **メモリ上の変数はリセットされる（インメモリ保存の禁止）**:
  サーバーレス関数はリクエストごとに別インスタンスが起動し、数分アクセスがないとコンテナが終了（スピンダウン）します。
  「アクセス数カウント」や「セッション管理」をメモリ上の変数（`Map` 等）に置くと消滅するため、**必ずSupabase等のDBやRedisに永続化**する。
- **クライアント露出の厳格管理**:
  Next.jsでは `NEXT_PUBLIC_` プレフィックスがついた環境変数のみがブラウザにバンドルされます。APIキー、サービスロールキー、秘密トークンには絶対に `NEXT_PUBLIC_` を付けない。

## 第3章：プロジェクト推進 ＆ 「やること管理」ノウハウ

### 1. 3層マネジメント分業体制

プロジェクトを停滞させず、品質を高く保ち続けるための基本体制：

```
┌──────────────────────────────────────────────┐
│ ① オーナー / プロダクトマネージャー (PO)     │
│   ・ビジョン、事業方針、最終決定、承認       │
└──────────────────────┬───────────────────────┘
                       │ (方針指示・壁打ち)
┌──────────────────────▼───────────────────────┐
│ ② 統括担当 / PM / アーキテクト               │
│   ・要件定義、仕様書作成、試算、品質監査     │
└──────────────────────┬───────────────────────┘
                       │ (明確な指示書・SPEC)
┌──────────────────────▼───────────────────────┐
│ ③ 実務担当 / エンジニア / AIサブエージェント │
│   ・コード実装、単体/結合テスト、デプロイ    │
└──────────────────────────────────────────────┘
```

---

### 2. 「勝手に直さない」意思決定・監査プロトコル

開発が進むと、予期せぬ不整合やバグ予備軍、文言の食い違いが発生します。この際の鉄則は以下の通りです：

> **【原則】問題を発見しても、勝手にコードを書き換えない**
> 1. **検知・整理**: どこに何の懸念・問題があるかを特定する。
> 2. **選択肢・修正案の提示**: 「案A（推奨）」「案B」など具体的な対応策を整理する。
> 3. **オーナーへの判断仰ぎ**: チャットやミーティングで報告し、承認を得る。
> 4. **実務指示・検証**: 承認された方針に沿って実装を行い、テストで検証した後に完了報告を行う。

このステップを踏むことで、「作った後でオーナーの意図と違っていた」「仕様変更の連鎖でデグレ（既存機能の破壊）が起きた」という手戻りをゼロに抑えられます。

---

### 3. ドキュメント体系の標準テンプレート

プロジェクト直下の `management/` または `docs/` に以下の5つのドキュメントを設けることで、状況が常に一目で把握できます。

| ファイル名 | 役割・内容 | 更新頻度 |
|:---|:---|:---|
| **`PROGRESS_MEMO.md`** | **全体進捗 ＆ 決定事項マスター**<br>現在のフェーズ、決定済み方針、直近のアクションアイテム。 | 決定事項発生ごと |
| **`FEEDBACK_LOG.md`** | **ユーザー・テスターの声（VoC）管理簿**<br>受信日、ユーザー属性、種別（UI/バグ/要望）、対応状況。 | フィードバック受領ごと |
| **`weeklylog.md`** | **週次定点振り返りログ**<br>決定したこと、実装した内容、課題と解決策、学びの蓄積。 | 毎週1回（月曜朝等） |
| **`SYSTEM_SPECIFICATION.md`** | **サービス・基本仕様設計書**<br>プラン体系、利用制限、AI/API原価、DBテーブル定義、運用ルール。 | 仕様変更時（即時更新） |
| **`XXXX_SPEC.md`** | **機能単位の実装指示書**<br>背景、画面・API要件、テスト要件、影響範囲を記述。 | 実装タスク着手ごと |

## 第4章：事業採算・コスト管理 ＆ リスク自動計算ノウハウ

API従量課金モデル（AI、SMS、音声合成等）を組み込んだSaaSでは、「ユーザーが使えば使うほど赤字になる」というリスクを技術的に排除しなければなりません。

### 1. 1回あたりの原価シミュレーション
- **入出力トークン数・秒数の実測**:
  概算ではなく、実際のAPIレスポンスから消費量（例: 音声文字起こし1回約0.15円、文生成0.02円等）を実測する。
- **キャッシュによる原価圧縮**:
  同一の入力に対しては、クライアントキャッシュやサーバーキャッシュを活用し、2回目以降のAPIコールをスキップして原価を大幅削減する。

---

### 2. 顧客ごとの損益分岐点（採算限界）の自動計算式

有料プランを「使い放題（上限なし）」にする場合、管理画面で各顧客の利用状況を自動監視するロジックを組み込みます。

$$\text{1人あたり月間損益分岐回数} = \frac{\text{月額料金} - \text{決済手数料 (約3.6\%)}}{\text{1回あたり実質原価}}$$

$$\text{1日あたり採算限界回数} = \frac{\text{月間損益分岐回数}}{30\text{日}}$$

#### リスク判定ロジックの実装例:
- **🟢 安全 (Safe)**: 1日平均利用数が限界の **50%未満** ➔ 健全な黒字
- **🟡 注意 (Warning)**: 1日平均利用数が限界の **50%〜80%** ➔ ややヘビー利用
- **🔴 警戒 (Danger)**: 1日平均利用数が限界の **80%以上** ➔ 赤字化リスク接近（アカウント利用確認）

管理画面（Admin Dashboard）にこのステータスを自動表示させておくことで、サービスを「使い放題」として魅力的に打ち出しつつ、事業リスクを完全にコントロールできます。

## 第5章：新規プロジェクト立ち上げ時のチェックリスト

新規SaaSを企画・開発する際、以下のステップ順に進めることで最短期間で安全にローンチできます。

### 【Stage 0】MVP（最小実用製品）構築 ＆ コア体験検証
- [ ] Next.js + Tailwind CSS による高速フロントエンド環境構築
- [ ] 主要なコアドメイン機能（提供価値の核心）の動作検証
- [ ] ゲスト体験（LocalStorage一時保存）の実装
- [ ] ユニットテスト環境（Vitest / Jest）の整備

### 【Stage 1】認証・課金・法務インフラ整備
- [ ] Supabase Auth（メール認証 / Google OAuth）の導入
- [ ] データベース設計 ＆ RLS（行単位セキュリティ）の完全適用
- [ ] Stripe Checkout ＆ Webhook によるサブスクリプション決済基盤
- [ ] 法務画面の整備（利用規約 `/terms`、プライバシーポリシー `/privacy`、特商法表記 `/tokushoho`）

### 【Stage 2】クローズドβ ＆ 定着率検証
- [ ] 友人・知人・限定テスター30〜50名の招待
- [ ] アプリ内不具合報告・問い合わせ機能の設置（メール自動通知連携）
- [ ] 行動トラッキング / アクセス解析基盤の導入（Vercel Analytics等）
- [ ] 習慣化・ストリーク（継続日数）機能の実装

### 【Stage 3】パブリックローンチ ＆ 収益化始動
- [ ] LP（ランディングページ）の最適化 ＆ SEOメタタグ整備
- [ ] SNS・開発者コミュニティ等でのパブリック公開
- [ ] 顧客管理画面（Admin）によるアクティブ率・採算限界の定点監視
- [ ] 週次振り返りログによる改善サイクルの高速回転

GitHub、Vercel、Supabaseという強力なクラウド基盤の上で、本プレイブックの設計と推進プロセスを適用することで、高品質なWebサービスを極小のリスクで素早く市場に届けることが可能になります。
