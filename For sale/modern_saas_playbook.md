# モダンSaaS開発 ＆ プロジェクト推進 総合プレイブック
## GitHub × Vercel × Supabase を用いた高速開発・ゼロ待ち時間UX・採算管理・やること管理ノウハウ

**最終更新**: 2026年10月1日（第2版：ハイブリッド問題バンク・0.0秒先読み・管理者Feature Toggle・2フェーズ原価管理・4大抜け漏れ防止プロトコル反映）

## はじめに
本ドキュメントは、Next.js、GitHub、Vercel、Supabase、および外部決済・生成AI APIを組み合わせてWebサービス（SaaS）を迅速かつ安全に立ち上げ・スケールさせるための**システム設計アーキテクチャ**および**プロジェクト推進（やること管理・意思決定・コスト統制）のノウハウ**を体系化した汎用プレイブックです。

特定のサービス名やドメインに依存せず、新規事業や別プロダクトの立ち上げ時に、技術選定、AIマルチエージェント分業、コスト圧縮、データ整合性、タスク管理の標準テンプレートとしてそのまま活用できます。

#### ① なぜこの構成が最強なのか？
- **インフラ管理工数ゼロ（サーバーレス）**:
  OSアップデートやサーバー監視、スケーリング対応が一切不要。ユーザーが0人の時はほぼ無料、トラフィック急増時も自動スケール。
- **デプロイの自動化と安全性**:
  GitHubにコミットしてプッシュするだけで、Vercelが自動ビルド・静的最適化・プレビュー環境生成を行い、本番反映まで数分で完了。
- **バックエンドの即時立ち上げ**:
  Supabaseにより、PostgreSQLデータベース、認証（メール/Google OAuth等）、ファイルストレージ、Row Level Security（行単位セキュリティ）が一元提供される。

### 2. オフラインファースト ＆ 未同期データの「自動レスキュー同期」設計

B2Cや習慣化SaaSでは、「ネット環境が不安定でも快適に動く」「登録前にすぐ試せる」「複数端末でデータが絶対に消えない」ことがCVR（登録率）と継続率を大きく左右します。

```
【未ログイン時 (ゲスト)】
  ユーザー操作 ➔ ブラウザ LocalStorage / IndexedDB に一時保存 (超高速・即時)

【ログイン / 会員登録時】
  認証完了 ➔ LocalStorage のデータを Supabase クラウドへ自動アップロード (初回Migration)

【日常利用時 (リアルタイム保存 ＋ 自動レスキュー同期)】
  アクション完了 ➔ ローカル保存と同時に Supabase へリアルタイム INSERT
  画面起動時     ➔ ローカルにあるがクラウドに未反映のレコード（localOnly）を自動検出し、バックグラウンドでレスキュー同期
```

#### 実装のポイント:
1. **ゲスト体験（登録不要体験）**:
   最初の数回は会員登録なしで利用させ、価値を体感させた後に「クラウド保存・端末間同期」をフックにして会員登録を促す。
2. **リアルタイム保存と自動レスキュー同期（Auto-Rescue Sync）**:
   通信瞬断やブラウザ閉じによってクラウド保存が漏れた場合でも、次回アプリ起動時に「ローカルIDとクラウドIDの差分」を検査し、未同期データを自動的にクラウドへ救出・アップロードする。
3. **スキーマ・マッピングの一貫性**:
   ローカル保存用オブジェクトとDBカラム名（例: スコアや速度指標など）の変換アダプターを1箇所に集約し、パイプライン途中でのデータ欠落を防ぐ。

### 3. 生成AIの「5秒待ち」を「0.0秒」にするハイブリッド先読み＆バンク設計

LLM（文章生成）やTTS（音声合成）などの生成AI APIは、リアルタイムに呼び出すと **3〜5秒の待ち時間** が発生し、ユーザーの学習・操作テンポを大きく損ないます。さらに毎回APIを叩くと従量課金コストが膨らみます。これを以下の2段階アーキテクチャで解決します。

```
【対策①：クライアント側バックグラウンド1件先読み (Client Prefetch)】
  1問目を操作・閲覧中 ➔ 裏側（非同期）で「次の1問（テキスト＋音声）」を先読み取得しメモリ（Ref）に待機
  「次へ」ボタン押下  ➔ メモリから即時スワップ描画（体感待ち時間 0.0秒！）

【対策②：DBコンテンツバンク蓄積 ＆ 週次10%ローテーション (Shared Bank)】
  初期〜蓄積期（各カテゴリ上限300件未満）:
    AIで動的生成しつつ、生成された良質なコンテンツ＋音声を Supabase の `content_bank` テーブルへ自動保存
  定常運用期（上限300件到達後）:
    AI APIを叩かず、DBバンクから未消化コンテンツを 0.1秒・API原価0円 で即時配信！
  鮮度維持バッチ（週1回 `/api/.../rotate`）:
    各カテゴリの「使用回数が多い上位10%（30件）」だけを、季節感や最新トレンドを入れたプロンプトで週1回入れ替え
```

#### この設計がもたらす3大メリット:
- **初期一括生成コストの回避**: 最初から数千件を一気に生成して高額な初期API費用を払うのではなく、実際のユーザー利用の裏で自然にバンクを貯められる。
- **体感待ち時間 0.0秒**: 先読みキャッシュとDB配信の組み合わせにより、ネイティブアプリ並みの瞬間遷移を実現。
- **API変動原価を 70〜80% 削減**: 定常期は生成コストがゼロになり、週1回の10%入れ替え（月額数百円の固定費）だけで常に新鮮なコンテンツを提供し続けられる。

## 第2章：セキュリティ ＆ データ整合性の鉄則

### 1. Row Level Security (RLS) の徹底と管理者権限の厳格化
Supabaseの最大の特徴は、フロントエンドから直接データベースを叩ける手軽さですが、**RLS（行単位セキュリティ）を有効にしないと他人のデータを改ざん・閲覧される致命的事故**に繋がります。

- **全テーブルで `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;` を適用**。
- **基本ポリシー**:
  ```sql
  -- 本人のみ読み取り・書き込み可能
  CREATE POLICY "Users can view own data" ON public.user_records
    FOR SELECT USING (auth.uid() = user_id);
  CREATE POLICY "Users can insert own data" ON public.user_records
    FOR INSERT WITH CHECK (auth.uid() = user_id);
  ```
- **管理者処理の分離と単一アカウント厳格化**:
  全顧客の集計や定期バッチは、サーバーサイドAPIからのみ呼び出せる `SUPABASE_SERVICE_ROLE_KEY`（管理者秘密鍵）を用いて実行する。また、管理者画面（`/admin/*`）やテストモードの許可リスト（`isAdminEmail`）は、開発用ダミーアドレスを残さず**本番オーナーの単一メールアドレスのみに厳格化**する。

---

### 2. 決済情報の完全非保持化 (PCI-DSS準拠)
個人開発やスタートアップで自社サーバーにクレジットカード番号を保持・通過させることはセキュリティ・法務上、絶対に避けるべきです。

- **Stripe Checkout / Customer Portal の全面採用**:
  カード入力画面はすべてStripeが提供する堅牢なUIを使い、自社サイトは一切触らない。
- **Webhookによる非同期ステータス更新**:
  Stripe側での決済完了・解約・更新イベント（`invoice.payment_succeeded`, `customer.subscription.deleted` 等）をWebhookで受け取り、Supabaseのユーザーテーブルのプラン区分を自動更新する。

---

### 3. 環境変数の管理とサーバーレスの特性理解
Vercel等のサーバーレス環境では、以下の点に注意が必要です：

- **メモリ上の変数はリセットされる（インメモリ保存の禁止）**:
  サーバーレス関数はリクエストごとに別インスタンスが起動し、数分アクセスがないとコンテナが終了（スピンダウン）します。
  「アクセス数カウント（PV/UU）」や「レート制限」をメモリ上の変数（`Map` 等）だけに置くと再起動時に消滅するため、**必ずSupabaseのテーブル（例: `daily_analytics`）等に永続化**し、DB接続障害時のみインメモリへフォールバックする二段構えにする。
- **環境変数名の多段フォールバック**:
  VercelとSupabaseの自動連携プラグイン等を使うと、環境変数名が `NEXT_PUBLIC_SUPABASE_SUPABASE_URL` のように重複プレフィックスになるケースがある。初期化コード側で標準キーと重複キーの両方を検査する多段フォールバックを入れておくと、本番デプロイ時の接続落ちを防げる。

### 2. 「勝手に直さない」意思決定・監査プロトコル

開発が進むと、予期せぬ不整合やバグ予備軍、文言の食い違いが発生します。この際の鉄則は以下の通りです：

> **【原則】問題を発見しても、勝手にコードを書き換えない**
> 1. **検知・整理**: どこに何の懸念・問題があるかを特定する。
> 2. **選択肢・修正案の提示**: 「案A（推奨）」「案B」など具体的な対応策とコスト・UX影響を整理する。
> 3. **オーナーへの判断仰ぎ**: チャットで報告し、承認を得る。
> 4. **実務指示・検証**: 承認された方針に沿って実装を行い、テストで検証した後に完了報告を行う。

---

### 3. コミュニケーションの抜け漏れを根絶する「4大プロトコル」

チャットやブレストの中で出たアイデアや改善要望が、実装担当へ落ちずに流れてしまう「タスクの抜け漏れ」を防ぐため、以下の4つの仕組みを徹底します：

1. **① 即時トリアージ＆復唱確認**:
   オーナーから要望やアイデアが出た瞬間、「いつのフェーズでやるか」「優先度はいくつか」をその場で復唱・合意する。
2. **② 会話のその場で `FEEDBACK_LOG.md` へ起票**:
   後回しにせず、会話のターン内で必ず通し番号（`FB-001` 等）を振って管理簿ファイルに書き込む。
3. **③ 週次定期点検での放置チケット強制スキャン**:
   毎週月曜朝などの定期バッチ点検にて、`FEEDBACK_LOG.md` と `PROGRESS_MEMO.md` で「起票・仕様策定中」のまま止まっている項目をスキャンし、オーナーへリマインドする。
4. **④ 統括HTMLダッシュボードでの可視化**:
   Markdownだけでなく、ブラウザで開ける統括ダッシュボード（`management.html`）に最新ステータスを同期し、視覚的に進捗を共有する。

### 4. 本番環境で安全に新機能を試す「管理者限定プレビュー（Feature Toggle）」

クローズドβや本番稼働中に、新しいUIや実験的な機能（例: 新しい録音方式や補助記号表示など）をいきなり全ユーザーに出すと、思わぬ混乱やバグを招きます。

```
[新機能の実装]
      │
      ▼
【Step 1: 管理者限定プレビュー (isAdminEmail / 🧪 テストボタンモード)】
  ・一般ユーザーやテスターの画面には 1px も影響を与えない
  ・管理者アカウントでログインした時だけ、新機能UIや切替トグルを表示して実機検証
      │
      ▼ (オーナーが実機で使い勝手を検証・ブラッシュアップ)
【Step 2: 全ユーザーへの標準昇格 (General Rollout)】
  ・完成度が確認できたらフラグを標準ONに切り替え、全ユーザーへ解放！
```

## 第4章：事業採算・2フェーズ原価管理 ＆ リスク自動計算ノウハウ

API従量課金モデル（AI、音声認識、音声合成等）を組み込んだSaaSでは、「ユーザーが使えば使うほど赤字になる」リスクを設計と管理画面の両面で排除します。

### 1. 2フェーズ原価管理モデル（蓄積期 ➔ バンク定常運用期）
コンテンツバンク方式を採用する場合、以下の2つのフェーズに分けて収支と損益分岐点を管理します。

| 項目 | 📘 フェーズA：バンク蓄積期（保守上限） | 🏦 フェーズB：バンク定常運用期（本命） |
|:---|:---|:---|
| **フェーズ定義** | 各カテゴリのコンテンツが上限（例: 300件）に達するまでの期間 | 上限到達後、DBから即時配信＋週1回10%入れ替えを行う期間 |
| **1回あたり変動原価** | 生成API ＋ 解析API（例: **約 0.322 円 / 回**） | 解析APIのみ・生成0円（例: **約 0.097 円 / 回** ➔ **約70%圧縮**） |
| **コンテンツ更新固定費** | 0円（都度生成に含む） | 週1回10%ローテーション（例: **月額 約 331 円** の完全固定費） |
| **50名規模での営業利益率** | **約 55% 〜 58%** | **約 79% 〜 80%** |

> 💡 **ポイント**: 管理画面（`/admin/customers`）での赤字リスク監視には、安全マージンをとってあえて厳しい方の「フェーズA（`@0.322円/回`）」を基準値として使用することで、万が一のコスト超過も確実に防ぎます。

---

### 2. 顧客ごとの損益分岐点（採算限界）の自動計算式と日次グラフ監視

有料プランを「使い放題（上限なし）」にする場合、管理画面（`/admin/customers`）で各顧客の利用状況を自動監視します。

$$\text{1人あたり月間損益分岐回数} = \frac{\text{月額料金} - \text{決済手数料 (約3.6\%)}}{\text{1回あたり実質原価}}$$

$$\text{1日あたり採算限界回数} = \frac{\text{月間損益分岐回数}}{30\text{日}}$$

#### 管理画面（`/admin/customers`）に実装すべき4大モニタリング機能:
1. **採算リスクバッジの自動表示**:
   - **🟢 安全 (Safe)**: 1日平均利用数が限界の **50%未満**
   - **🟡 注意 (Warning)**: 1日平均利用数が限界の **50%〜80%**
   - **🔴 警戒 (Danger)**: 1日平均利用数が限界の **80%以上**
2. **メンバー別「日次利用回数折れ線グラフ」モーダル**:
   各ユーザーの「利用回数」ボタンをクリックすると、日別の利用推移を折れ線グラフ＋サマリー（合計・1日平均・最高記録）でポップアップ表示し、急激なスパイクや定着度を視覚的に把握。
3. **プラン別契約内訳（Pro / Basic）とモバイル用カード切替**:
   外出先（スマホ）からでも顧客状況を快適にチェックできるよう、テーブル表示とカード表示のワンタップ切替を搭載。
4. **コンプライアンス監査ログのタブ統合**:
   管理画面のURLを分散させず、顧客一覧画面のタブ切り替えでコンプライアンス・セキュリティ監査ログも一元確認できるようにする。

## 第5章：新規プロジェクト立ち上げ時のチェックリスト

新規SaaSを企画・開発する際、以下のステップ順に進めることで最短期間で安全にローンチできます。

### 【Stage 0】MVP（最小実用製品）構築 ＆ コア体験検証
- [ ] Next.js + Tailwind CSS による高速フロントエンド環境構築
- [ ] 主要なコアドメイン機能（提供価値の核心）の動作検証
- [ ] ゲスト体験（LocalStorage一時保存）の実装
- [ ] ユニット・統合テスト環境（Vitest / Jest）の整備

## まとめ
SaaS開発において最も重要なのは、**「ユーザーを待たせない0.0秒の快適UXと低原価を両立するアーキテクチャ」**、そして**「透明性の高いやること管理・勝手に直さないガバナンス・抜け漏れゼロの記録体制」**です。
GitHub、Vercel、Supabaseという強力なクラウド基盤の上で、本プレイブックの設計と推進プロセスを適用することで、高品質・高収益なWebサービスを極小のリスクで素早く市場に届けることが可能になります。
